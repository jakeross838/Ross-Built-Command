## Strategies considered

### Strategy 1-prime — entity_type-aware UI label mapping (RECOMMENDED — primary)

Application code preserves entity_type='invoice' / 'draw' literal values in writes (existing enum unchanged).
UI components reading audit_log map entity_type to user-facing label via src/lib/audit/action-labels.ts helper.

Helper module: src/lib/audit/action-labels.ts (~30 LOC; this Plan 2 ships).

Usage:
```typescript
import { auditLabel } from "@/lib/audit/action-labels";

const row = await supabase.from("activity_log").select("...").single();
const { summary } = auditLabel(row.entity_type, row.action);
// summary: "Bill approved" or "Pay App created" etc.
```

**Pros:**
- No DB migration required in 1.5c
- Historical audit_log rows display correctly with new terminology
- F1 may add new entity_type enum values without breaking existing rows
- Future-proofs UI without locking schema decisions

**Cons:**
- Two layers of terminology (DB enum: 'invoice' / 'draw'; UI: 'Bill' / 'Pay App')
- Requires every audit-log-displaying component to import the helper

**Verdict: Recommended for 1.5c.** Lowest risk, smallest blast radius, F1-flexible.

### Strategy 2 — Migrate enum + rows atomically

Migration adds 'bill' + 'pay_app' enum values. Update statement migrates all existing rows. All callers updated to write new values.

**Pros:**
- Single vocabulary post-migration
- No UI helper needed

**Cons:**
- Migration touches every audit_log row (production data growth)
- Migration is destructive (audit-trail-mutation concern)
- Coordination cost: every existing call site updated atomically with the migration

**Verdict: Defer to F1.** Plan 2 documents but does NOT execute.

### Strategy 3 — Application-layer translation at write time

Application code accepts new vocabulary but writes legacy to DB. UI reads DB and applies same UI label mapping.

**Verdict: Rejected.** Strategy 1-prime gives same UI consistency without translation-at-write complexity.
