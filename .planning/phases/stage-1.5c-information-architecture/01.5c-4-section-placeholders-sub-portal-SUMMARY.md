## iter-2 mechanical #5 (a) — Sub Portal param-reflection grep verify

`grep -E "params\.token" src/app/sub-portal/magic/[token]/page.tsx src/app/sub-portal/public/[token]/page.tsx` returns 0.

Both stubs accept the `[token]` URL segment (so F3 magic-link emails can address the route correctly) but never read or reflect the token value. XSS surface prevented at design time. F3 will validate token + scope at the route-handler level server-side, not in the page component.

## iter-2 mechanical #5 (b) — Sub Portal F3 compliance contract

Both magic + public stubs explicitly document:

1. **Token expiry** — magic: 30-day default (configurable per email type); public: 90-day default (configurable per share)
2. **Scope binding** — magic: single job + single document; public: single job + view-scope filter
3. **Audit-log-on-use** — both: every link follow logs `entity_type='client_portal_access' / action='accessed'` (mirror migration 00074)
4. **Cookie-vs-querystring** — magic: querystring single-use; public: querystring per-request validation
5. **JWT-with-org-claim REJECTED** — both: org_id leakage on stolen token is a vulnerability surface; server-side resolves scope from token hash
6. **Mirror client_portal_access pattern (migration 00074)** — both: SHA-256 hash + service-role-API + anon-grant + audit-log

Grep verify: "Token expiry"=1+1=2; "JWT-with-org-claim REJECTED"=1+1=2; "client_portal_access OR migration 00074 OR SHA-256"=4+3=7.
